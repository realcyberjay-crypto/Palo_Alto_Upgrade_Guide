Which Kind of Upgrade Is This?

A version number is an address: 12 is the city, .1 is the street, .4 is the house, -h2 is a new coat of paint on the same house. Moving house on the same street is easy. Moving to another city needs a map.

Reading a PAN-OS version:
   11 . 1 . 4 - h13
    |    |   |    |
    |    |   |    +-- HOTFIX       urgent fixes on top of a maintenance release
    |    |   +------- MAINTENANCE  bug fixes, same features
    |    +----------- FEATURE      new features, new behaviour
    +---------------- MAJOR        new generation (11 -> 12)

There is no PAN-OS 11.3 or 11.4. The feature releases run 10.1 → 10.2 → 11.0 → 11.1 → 11.2 → 12.1. When someone says "11.1 to 11.4" they almost always mean 11.1.x to 11.1.4 — a maintenance upgrade.

How to Check the Upgrade Path — Seven Checks

Before a long car trip you check four things: does the car go that far, which roads are open, where you must stop, and whether the people at home know you are coming. This page is that check list.

  1. Read what you run today. CLI: show system info | match "model|sw-version". GUI: Dashboard → General Information, or Device → Software (tick in Currently Installed).
  2. Can the hardware run the target? TechDocs → Compatibility Matrix → Supported OS Releases by Model. If your model has no tick under the target, stop — this is a hardware refresh, not an upgrade. Check the End-of-Life Summary for the support end date of the target too.
  3. Pick the target build, not just the release. Use Palo Alto's Support PAN-OS Software Release Guidance (LIVEcommunity) for the currently preferred maintenance release. On 11.1.3 and later, Device → Software → clear Base Releases to show preferred releases only.
  4. Read the path table. TechDocs → PAN-OS Upgrade Guide → Determine the Upgrade Path, with the version filter set to your target. Summary below.
  5. Panorama and friends first. Panorama, Log Collectors and WildFire appliances must be on the same or a later release than the firewalls. Check Panorama, Log Collector, Firewall, and WildFire Version Compatibility, and any plugin version tables (SD-WAN, DLP).
  6. Read the notes for every release on the path — including releases you skip. Release Notes (known issues, minimum content version), Upgrade/Downgrade Considerations and Changes to Default Behavior.
  7. Run the upgrade check report (standalone or from Panorama for managed firewalls) and clear its warnings before the window.

  • Never install a base image (x.y.0) unless it is your final target. Download it; do not install it.

How to Read the Command Blocks

New to Palo Alto? Every command block in this guide uses the same three colours. Once you know them you can read any block at a glance.

admin@fw-01(active)> show system info | match sw-version            what the command does
sw-version: 11.1.x-hN
ColourMeans
AmberThe command you type.
GreyPlain-English explanation. Not typed — it is a note to you.
GreenOutput you should expect back from the firewall.

The prompt tells you three things

admin@fw-01(active)>
     |      |       |
     |      |       +-- MODE: > is operational, # is configuration
     |      +---------- HA ROLE: active, passive, suspended, or blank if standalone
     +----------------- HOSTNAME: which firewall you are actually on
PromptWhere you are
>Operational mode. Look at things, run actions. Nothing here is saved config.
#Configuration mode. You got here with configure. Changes are staged until you commit.

Four verbs cover almost everything

VerbWhat it does
showRead-only. Safe to run any time, on any box, including during a change.
requestDo something now — download, install, reboot, suspend. Not saved config, but it acts immediately.
setConfiguration mode only. Stages a change that does nothing until you commit.
deleteRemoves something — a config line in # mode, or a file in > mode.

show is looking. request is doing. set is writing on a draft that nobody sees until commit publishes it.

Press Tab at any point to complete a command, and ? to see the valid options from where you are. On an unfamiliar release this beats guessing — the firewall will tell you exactly what it accepts.

OrientationPLANNING

The Upgrade Path — Rules That Bite Before You Type Anything

PAN-OS will not let you jump wherever you like. Three constraints govern the path, and violating any of them turns a clean maintenance window into a long night.

  1. You can now skip feature releases — within limits. The Skip Software Version Upgrade feature (PAN-OS 10.1 and later) lets a firewall jump up to three releases. Palo Alto's current path table says 11.0, 11.1 and 11.2 can go directly to 12.1. Older releases (10.0 and earlier) still climb one step at a time. See Going to PAN-OS 12.1.
  2. A hotfix needs its base image on the box. To land on 11.1.4-h13 the firewall must already have 11.1.0 downloaded. The base image only needs downloading, not installing.
  3. HA peers cannot drift more than one feature release apart. When they do, the older peer suspends itself with the message Peer version too old. If your path has multiple hops, both peers must land on each intermediate release before you move on. This is the rule that collides with skipping — an HA pair jumping 11.1 → 12.1 is two releases apart mid-change. See the HA warning in Going to PAN-OS 12.1.

Think of it as a staircase with no handrail. On old releases you can only take one step at a time, you must both be standing on the same step before either of you climbs again, and the step has to be delivered before you can stand on it.

Read the currently installed version and the content versions in one shot:
admin@fw-01(active)> show system info | match "sw-version|app-version|threat-version|hostname"  version and content in one line — your baseline record
hostname: fw-01
sw-version: 11.1.x-hN
app-version: 8951-9143
threat-version: 8951-9143

The release notes for every version you pass through list minimum content release requirements and known issues. Reading only the release notes for your final target is the single most common planning mistake.

2 · Which path?

11.2.xDirect to 12.1 (skip)Direct to 12.1 — one feature release apart, normal HA rules

HA + skip is the open question. The Skip Software Version feature is documented for standalone and Panorama-managed devices. The HA rule says peers two or more feature releases apart suspend the older one with Peer version too old. If you skip 11.1 → 12.1 on an HA pair, the peers sit two releases apart between the first and second reboot — with no redundancy while that lasts. Until the 12.1 HA upgrade page or TAC confirms otherwise, step HA pairs through 11.2.

3 · How a skip actually works

Download the target's base image and the target. Install ONLY the target.
admin@fw-01> request system software check                          refresh the list — skip-eligible 12.1 releases should now appear
admin@fw-01> request system software download version 12.1.0        base image — download only, never install
admin@fw-01> request system software download version <12.1 target> the release you will actually run
admin@fw-01> request system software install version <12.1 target>  one install, one reboot
  • Device → Software → Check Now. Download the 12.1 base image, then the 12.1 target. Install the target only.
  • If 12.1 is not listed after Check Now, the box is not skip-eligible — go via 11.2.

Remote AccessPRE-STAGE

Opening Remote Access Before the Window

Make sure you have the key to the house before you lock the door behind you.

An upgrade is the worst possible time to discover you cannot reach the firewall from where you actually are. Sort access out days ahead, from a session you already have, while the firewall is healthy.

Do this before you start, never during. Every method below needs a commit, and a commit needs a working management session. If you are locked out already, you are going to the console or the data centre — there is no remote fix for a lockout.

Permitted IP addresses on the management interface

If the management interface has a permitted-IP list, only those sources can reach it. Adding your remote source is the single most common pre-upgrade access task.

admin@fw-01(active)> configure                                                enter configuration mode — the prompt changes from > to #

See what is already allowed — Tab after permitted-ip lists the current entries:
admin@fw-01(active)# show deviceconfig system permitted-ip                    which source addresses may reach the management interface

Add your remote source. Always a /32 for a single host:
admin@fw-01(active)# set deviceconfig system permitted-ip 203.0.113.45/32 description "upgrade-window jump host"  allow one host to reach management — everything unlisted is then blocked
admin@fw-01(active)# commit                                                   apply the candidate config — nothing above is live until this runs
admin@fw-01(active)# exit                                                     leave configuration mode, back to the > prompt

GUI: Device → Setup → Management → edit Management Interface Settings → add the address under Permitted IP Addresses → OK → Commit.

The permitted-IP list is all-or-nothing. An empty list means any source may reach the management interface. The moment you add your first entry, everything not listed is blocked — including the session you are typing in right now. Add your current source address in the same commit, or you will cut yourself off the instant it applies.

If Panorama pushes the list via a template

A template-pushed permitted-ip cannot be edited locally until you override it:

admin@fw-01(active)# set deviceconfig system permitted-ip 203.0.113.45/32  allow that source address to reach the management interface
Server error : set failed, may need to override template object permitted-ip first

admin@fw-01(active)# override deviceconfig system permitted-ip             break the Panorama template lock so you can edit this locally
admin@fw-01(active)# set deviceconfig system permitted-ip 203.0.113.45/32  allow that source address to reach the management interface
admin@fw-01(active)# commit                                                apply the candidate config — nothing above is live until this runs

Cleaner alternative: add the entry to the Panorama template and push it to both peers at once. The local override works, but it drifts the firewall from its template and someone will "fix" that later by re-pushing — removing your access.

Remote AccessACCESS PATHS

Access Paths, Best to Worst

There is more than one way to reach a firewall remotely, and they are not equally good ideas. In order of preference:

MethodVerdict
Out-of-band console (terminal server / iLO)Best. Survives a failed boot, a bad commit and a wrong permitted-IP entry. The only path that works when the firewall does not.
VPN to the management network, then SSHVery good. No firewall management exposed publicly. Nothing to undo afterwards.
Jump host on the management networkGood. One permitted-IP entry, permanent, auditable.
GlobalProtect on the firewall itselfCareful. Fine day to day, useless when the box is mid-reboot — the thing you need access to is the thing that is down.
Interface management profile on a data interfaceLast resort. Works, but you are putting the management plane on a traffic-carrying interface.
Management interface directly on a public IPDo not. See the warning below.

Interface management profile on a data-plane interface

When there is genuinely no other path, you can enable SSH and HTTPS on a data interface's IP. Three things must all be right: the profile, the interface it is attached to, and a security policy permitting the traffic.

admin@fw-01(active)> configure                                                enter configuration mode — the prompt changes from > to #

1. Build a tightly scoped profile:
admin@fw-01(active)# set network profiles interface-management-profile MGMT-TEMP https yes  allow the web interface on whichever interface gets this profile
admin@fw-01(active)# set network profiles interface-management-profile MGMT-TEMP ssh yes  allow SSH on whichever interface gets this profile
admin@fw-01(active)# set network profiles interface-management-profile MGMT-TEMP ping yes  allow ping, so you can test reachability
admin@fw-01(active)# set network profiles interface-management-profile MGMT-TEMP permitted-ip 203.0.113.45/32  restrict it to one source — this is the whole security control

2. Attach it to the interface:
admin@fw-01(active)# set network interface ethernet ethernet1/1 layer3 interface-management-profile MGMT-TEMP  attach the profile to a data interface so its IP answers SSH and HTTPS
admin@fw-01(active)# commit                                                   apply the candidate config — nothing above is live until this runs
admin@fw-01(active)# exit                                                     leave configuration mode, back to the > prompt

3. Verify it took:
admin@fw-01(active)> show interface ethernet1/1                               detail for one interface, including any management profile applied

GUI: Network → Network Profiles → Interface Mgmt → Add. Then Network → Interfaces → the interface → Advanced → Management Profile.

Never expose the management plane to the internet without a source restriction. The permitted-ip inside the interface management profile is not optional decoration — it is the whole control. Palo Alto management interfaces have been actively scanned and exploited in the wild; an unrestricted HTTPS management surface on a public address will be found in hours, not weeks.

Name the profile something obviously temporary — MGMT-TEMP, not MGMT. Add its removal to the change closure checklist alongside re-enabling preemption. Temporary access that nobody removes is how a maintenance convenience becomes next year's audit finding.

Removing it afterwards

admin@fw-01(active)# delete network interface ethernet ethernet1/1 layer3 interface-management-profile  detach the profile — do this as soon as the change closes
admin@fw-01(active)# delete network profiles interface-management-profile MGMT-TEMP  remove the temporary profile entirely
admin@fw-01(active)# commit                                                   apply the candidate config — nothing above is live until this runs

Put a name sticker on each window. You do not want to switch off the wrong firewall.

Three Backups — Snapshot, Config Export, Device State

Save your homework on the computer and on a USB stick. If the computer breaks, the stick still has it.

These are different things and people routinely conflate them. Do all three, on both peers.

On-box named snapshot

admin@fw-01(active)> configure                                                enter configuration mode — the prompt changes from > to #
admin@fw-01(active)# save config to Pre_Upgrade_2026-08-24.xml                snapshot the config to the firewall's OWN disk — convenient, not a real backup
admin@fw-01(active)# exit                                                     leave configuration mode, back to the > prompt

Confirm it landed:
admin@fw-01(active)> show config saved Pre_Upgrade_2026-08-24.xml | match hostname  prove the snapshot exists and is readable

Off-box export

admin@fw-01(active)> scp export configuration from running-config.xml to user@10.20.30.40:/backups/fw-01-pre.xml  copy the live config to a remote server — THIS is the real backup
or, if you use TFTP:
admin@fw-01(active)> tftp export configuration from running-config.xml to 10.20.30.40  same thing over TFTP if you have no SCP target

Device state export — the fullest restore bundle

admin@fw-01(active)> configure                                                enter configuration mode
admin@fw-01(active)# save device-state                                        build device_state_cfg.tgz in /opt/pancfg/mgmt/device-state — Tab-complete to confirm on your release
admin@fw-01(active)# exit
admin@fw-01(active)> scp export device-state to user@10.20.30.40:/backups/        copy the bundle off the box
or:
admin@fw-01(active)> tftp export device-state to 10.20.30.40
BackupContainsUse it to
Named snapshot (on-box)Local running configQuick revert on a healthy box
Config export (off-box)Local running config only — not what Panorama pushedRebuild or roll back a standalone / locally managed firewall
Device state (off-box)Running config plus Panorama-pushed device-group and template settings. On a GlobalProtect portal, also its certificates and satellite list.Replace a dead firewall with a new one — import the bundle on the replacement

Device state is not "everything". It does not hold licences (re-fetch them from the support portal on a replacement), logs, software images or dynamic content. Encrypted secrets in the config are tied to the master key — if you use a custom master key, record it (securely) or the restored secrets will not decrypt.

The named snapshot lives on the firewall's own disk. If the appliance fails to boot, that copy is unreachable. The off-box export is the one that actually protects you — treat the snapshot as a convenience, not a backup.

  • Device → Setup → Operations → Save named configuration snapshot (on-box), then Export named configuration snapshot → running-config.xml (off-box, via browser), then Export device state (full bundle, via browser). Full walkthrough: Backing Up Without an SCP Server.

HA PreparationHA PREP

Disable Preemption

Tell the bossy goalkeeper: "Do not grab the gloves back the second you walk in." Otherwise he grabs them while he is still tying his shoes.

Preemption makes the higher-priority peer grab the active role back the moment it is capable of it. During an upgrade that means an unplanned failover at the exact moment a freshly rebooted, newly-versioned firewall comes up. Turn it off first.

Read the current setting before changing it:
admin@fw-01(active)> configure                                                enter configuration mode — the prompt changes from > to #
admin@fw-01(active)# show deviceconfig high-availability group election-option  read the current preemption setting before you change it
preemptive yes;

admin@fw-01(active)# set deviceconfig high-availability group election-option preemptive no  stop the higher-priority peer grabbing back the active role mid-upgrade
admin@fw-01(active)# commit                                                   apply the candidate config — nothing above is live until this runs
admin@fw-01(active)# exit                                                     leave configuration mode, back to the > prompt

Verify from operational mode:
admin@fw-01(active)> show high-availability state | match Preempt             is preemption on or off right now
Preemptive: no

The path is high-availability group election-option — with no group ID in it. On PAN-OS 7.0 and later the HA group is a single node; group-id is a value you set beneath it, not a selector you index into. See Syntax Corrections.

You only need to disable preemption on one peer, but the commit must succeed before you proceed. If you prefer belt-and-braces, doing it on both is harmless.

  • Device → High Availability → General → edit Election Settings → clear Preemptive → OK → Commit. Confirm the commit succeeded before going on.

HA UpgradeSEQUENCE

The Active/Passive Sequence

Two goalkeepers. One steps off to change boots while the other guards the net. Then they swap. The net is never empty.

Palo Alto's current documented manual procedure for active/passive is active-first: suspend the active peer to force a failover, upgrade it, return it to functional, then suspend the secondary and upgrade that.

The passive-first variant. Many field runbooks — including plenty that work fine — upgrade the passive peer first, verify it carries traffic after a deliberate failover, then upgrade the original active. That order tests the newly-upgraded box before committing both peers to the new version, which some teams prefer. Both orders are safe. What matters is that only one peer is ever out of service, and that you know which order you are following before you start.

HA UpgradeSTEP 1

Suspend the Peer You Are About to Upgrade

Put up a "back in 5 minutes" sign. The other shop opens and customers walk next door.

Suspending removes the firewall from HA participation. It stops passing traffic and stops competing for the active role. This is what makes the upgrade safe.

admin@fw-01(active)> request high-availability state suspend        take THIS firewall out of HA — it stops passing traffic, peer takes over

Confirm — prompt changes and state reports suspended:
admin@fw-01(suspended)>
admin@fw-01(suspended)> show high-availability state | match State  local and peer role in two lines
Local Information: State: suspended
Peer Information: State: active

Verify from the other peer that it actually took over, and that traffic is genuinely flowing — do not take the state output as proof of service.

admin@fw-02(active)> show session info                           session count and how full the session table is
admin@fw-02(active)> show session all | match "flow|proto"       trim the session list to the useful columns
admin@fw-02(active)> show high-availability state | match State  local and peer role in two lines

This is your real failover test. If traffic does not recover here, stop — put the suspended peer back with request high-availability state functional and investigate. You have not installed anything yet, so nothing is lost. Discovering a broken failover after you have rebooted a peer onto a new version is a much worse place to be.

You can also drive the peer from the local box, which is useful when you only have a session to one side:

admin@fw-01(active)> request high-availability state peer suspend     suspend the OTHER firewall from this session
admin@fw-01(active)> request high-availability state peer functional  return the OTHER firewall to service from this session

Managing the Outage

The lights coming on does not mean the oven is hot. Wait until you see real cookies (sessions).

Panorama GUIHA SEQUENCE

HA Pairs From Panorama — Passive First

This ordering differs from the firewall-GUI procedure. The Panorama-driven procedure upgrades the passive peer first, verifies it, then suspends the active peer and upgrades that. The standalone firewall procedure earlier in this runbook goes active-first. Both are documented and both are safe — but decide which one you are following before you start, and do not mix them mid-change.

  1. Content to both peers — Panorama → Device Deployment → Dynamic Updates.
  2. Disable preemption on the first peer of each pair. Switch context to the firewall, Device → High Availability → Election Settings → clear Preemptive → Commit. One peer per pair is enough.
  3. Deploy to the passive peer. Panorama → Device Deployment → Software → Install on the right model row. Select only the passive peer of each pair (active-secondary for active/active). Group HA Peers cleared, Reboot device after install selected. OK.
  4. Wait for the reboot to finish. Do not start the next step early.
  5. Verify in Panorama → Managed Devices that the version is correct and the upgraded peer is still passive.
  6. Suspend the active peer. Switch context to it → Device → High Availability → Operational Commands → Suspend local device. The upgraded peer takes over — confirm traffic is flowing on it.
  7. Deploy to the now-suspended peer — same dialog, this time selecting the other half of each pair. Group HA Peers still cleared, Reboot device after install still selected.
  8. Wait for it to come back, then Make local device functional from its Operational Commands.
  9. Wait for config sync, then re-enable preemption where you disabled it.

Panorama does the boring, repeatable part — shipping images and rebooting. The judgement calls, suspend and make-functional, stay on the firewall. That division is why the Panorama path still needs someone watching each pair rather than one big OK button.

Step 6 is the failover test, exactly as in the CLI path. If traffic does not recover when you suspend the active peer, make it functional again and stop — at that point only one peer has been upgraded and you can still walk away cleanly.

Disk SpaceCLEANUP

Logs, Automatic Cleanup and Quotas

Logs are the last thing to reach for, not the first — they are your evidence trail, and they usually live on a partition that was not the problem anyway.

admin@fw-01(active)> clear log system   WIPE the system log — destructive, and it frees panlogs, not panrepo
admin@fw-01(active)> clear log traffic  WIPE the traffic log — you lose the audit trail
admin@fw-01(active)> clear log threat   WIPE the threat log — you lose the audit trail

Clearing logs is destructive and usually solves the wrong problem. Logs sit on /opt/panlogs, which is typically the emptiest partition on the box. If /opt/panrepo is full, clearing the system log frees nothing useful — deleting old images is what fixes it. Check show system disk-space first and clear the partition that is actually full.

Built-in cleanup

admin@fw-01(active)> debug software disk-usage cleanup deep threshold 90  run the built-in cleanup at 90% instead of the 95% default — not persistent

Runs the internal cleanup routine at a lower threshold than the 95% default. It is not persistent across reboots and must be re-run each time. It may remove backup log files, so it can cost you data you wanted for analysis.

Quotas — the durable fix

admin@fw-01(active)> show system logdb-quota  how much space each log type is allowed to consume

GUI: Device → Setup → Management → Logging and Reporting Settings. Reducing quotas is a real fix; clearing logs is a one-off that buys you until next month.

Alert on it. The firewall writes a system log entry along the lines of Disk usage for / exceeds limit, 95 percent in use, cleaning filesystem. If you forward syslog, build an alert on that string — then disk pressure reaches you weeks before it reaches an upgrade window.

Some partitions cannot be cleaned from the CLI at all, because the files need root access. If show system disk-space shows a partition full and nothing above touches it, that is a TAC case, not a puzzle to solve with clever commands. Do not go looking for a root shell.

> delete software version 11.1.4-h13                      remove an old image — never the running version or its base image
> delete software version 11.1.4-h7                       remove an old image — never the running version or its base image

> show system disk-space                                  free space per partition — run this BEFORE downloading anything
/opt/panrepo utilisation 80% -> 46%, roughly 4.1 GB reclaimed

Which step did the work. Step 3 is the one that fixed the blocked install — images and panrepo are the same partition. Step 1 helped a different partition that also benefits from headroom. Step 2 freed panlogs, which was almost certainly not the constraint. Worth knowing, because next time you can go straight to delete software version and keep your system log intact.

Before repeating this, check show system info | match sw-version and confirm you are not deleting the running version or its base image. In this case the box was running a 10.2 release, so removing 11.1 images was safe. On a firewall already running 11.1.4-h13, delete software version 11.1.4-h13 would be deleting the version underneath itself.

Download and Install Failures

Error or symptomCause and fix
There is not enough free disk space to complete the desired operationExactly what it says. show system disk-space, then delete old images. Remember the 90% rule on pancfg.

Upgrade FailuresPOST-REBOOT

It Rebooted and Something Is Wrong

SymptomWhat to do
Never comes back at allConsole access. Boot messages tell you far more than a dead SSH session. This is why out-of-band access is first on the list.
SSH answers but no traffic passesshow chassis-ready. If it returns no, the dataplane is still coming up — wait. If it stays no, check show system software status and the system log.
Still on the old versionThe install job did not complete before the reboot. Re-run request system software install version <target> and wait for FIN/OK this time.
Interfaces down that were up beforeCompare against your baseline capture. Check the release notes for changes to default behaviour — interface or link-speed defaults do occasionally change between releases.
Processes restarting in a loopshow system software status, then the system log. Grab a tech-support file and open a TAC case rather than rebooting repeatedly.
Certificates rejected after upgradePAN-OS 11.1 and later enforce OpenSSL Security Level 2 — RSA 2048 / ECDSA 256 minimum, SHA256 digest or better. Weak certificates must be regenerated or re-imported.
Config partly missingDo not commit anything. Load your pre-upgrade export: load config from <file>, review, then commit.

When a firewall is misbehaving after an upgrade, the instinct is to reboot it again. Resist that. Each reboot destroys volatile state that TAC would use to diagnose the problem, and if a process is crash-looping, another reboot changes nothing. Capture a tech-support file first.

Upgrade FailuresHA

HA Problems During and After Upgrade

SymptomCause and fix
Peer version too old, peer suspends itselfPeers are two or more feature releases apart. Bring the lagging peer up one release. Unavoidable if you skipped a hop — you must finish the staircase.
Both peers active after rebootSplit brain from an HA1 control link failure. show high-availability all and check HA1, HA1-backup and heartbeat backup. Restore the control link, then suspend the peer that should not be active and make it functional again once HA1 is up.
Failover fired mid-upgradePreemption was never actually disabled, or the commit silently failed. show high-availability state | match Preempt. This is why the commit must be confirmed before you proceed.
Config out-of-sync after both peers upgradedFrom the peer you trust: request high-availability sync-to-remote running-config. Direction matters — see Force a Config Sync.
Upgraded peer will not go passiveIt is still suspended. request high-availability state functional. If it refuses, check show chassis-ready first — a peer with a dataplane that is not up cannot become functional.
Sessions drop on every failover afterwardsHA2 session sync is not running. show high-availability interface ha2 and confirm the counters increment. See Confirming Session Sync.
Pair never fails backPreemption left disabled after the window. Re-enable and commit.
HA links flapping post-upgradeLink or path monitoring was re-enabled while the dataplane was still settling. Confirm show chassis-ready on both, then re-check show high-availability path-monitoring.

Nearly every HA problem in this table traces back to one of three things: the peers are too far apart in version, something that should have been disabled was not, or something that should have been re-enabled was not. Check those three before reaching for anything clever.

Field ReferenceKNOW BEFORE YOU TYPE

Commands That Bite

CommandWhat actually happens
request restart systemImmediate reboot, no confirmation, no grace period. On a standalone firewall this is the outage starting right now.
request high-availability state suspendRemoves the box from HA. Run it on the wrong peer and you have suspended the one carrying traffic while the other is mid-install.
request high-availability sync-to-remote running-configOverwrites the peer's running config with the local one. Direction is everything.
request system software installWrites to the alternate partition and marks it pending. Harmless until the reboot — but the next reboot for any reason will activate it.
commitOn an HA pair with config sync enabled, pushes to the peer as well. There is no "just on this box" commit.
set ... election-option preemptive yesIf the local box has higher priority, this can trigger an immediate failover on commit. Do it when you can tolerate one.
request system private-data-resetWipes configuration and logs to factory state. Present in the same command tree. Never during an upgrade.
load config from <file>Replaces the candidate config wholesale. The following commit replaces everything, including anything changed since the file was taken.
